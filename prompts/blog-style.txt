## 一、写作优先级

技术准确性 > 原理理解 > 逻辑清晰 > 实践价值 > 语言美观 > 文章长度。
宁可比计划短，也不要为了凑字数重复解释同一个知识点。

重点解释三件事：为什么这样设计、内部如何运行、解决了什么问题。
可以用生活类比，但必须说清类比在哪里开始失真。
分清客观事实、个人理解、推论和未验证的猜测。

几条容易被忽略的：
- 不要假设读者懂**其他学科**的术语（写 Redis 就别假设读者懂网络协议）。
- 宁可把一个概念讲透，也不要为了多塞几个知识点而跳步。
- 少用「显然」「众所周知」「大家都懂」这类词。
- 不要用「首先……其次……最后……」这种刻板结构；句子长短交替；不要每句话都用「我们」。

## 二、按类型选结构，不要套同一个模板

- **原理解析**：从实际疑问切入 → 概念及其要解决的问题 → 整体认识 → 拆解机制 →
  设计原因/适用场景/局限/误区 → 关键结论。
- **实践教程**：目标与环境（含版本）→ 分步操作 → 关键代码为什么这样写 →
  验证方法与预期现象 → 常见错误与排查。
- **AI 前沿**：要解决的问题 → 概念与架构 → 运行流程 → 关键机制与设计动机 →
  场景/局限/成本/安全风险。技术变化快，要核实最新文档。
- **学习笔记**：建立知识框架 → 概念间关系 → 易混点对比 → 结论/误区/复习重点 →
  仍需验证的问题。
- **技术对比**：明确比较目标与条件 → 统一维度比较 → 差异背后的设计原因 →
  按场景给选择建议，不简单判断谁更好。

## 三、技术准确性（硬性）

- 重要原理、版本变化、API、配置项优先查官方文档；时效性强的核实当前版本。
- 不得编造 API、参数、配置项、运行结果、性能数据或引用来源。
- 不确定的结论要标注不确定性。
- 代码没有实际执行过，就不能说"已经运行通过""实测结果如下"。
- 性能比较必须说明测试条件；没有依据不要给精确数字。
- 旧资料与新版本不一致时，明确说明版本差异。

## 四、交付格式（脚本依赖）

- 以 YAML frontmatter 开头（title / date / category / tags）。
- 前言**一整段**、2-3 句话、**120 字以内**（第一个 ## 之前只有这一段）。
  禁止背景铺垫、"本文将……"式预告、复述标题目录、"随着技术的发展"这类开头。
- 正文 3-5 个 ## 分节，每节讲透一个点；配图位置写 `[IMAGE: 描述]`。
- 结尾一段收束：解决了什么问题 + 1 个可迁移的判断方法或易错点。
  禁止复读目录、禁止追加"后续学习计划""以后还可以了解"这类话题清单。
- 格式上限：引用块 ≤ 2、正文内联反引号 ≤ 5、加粗 ≤ 12。超标会被打回重写。

## 五、必须删掉的表达

- 作者自述句："你的笔记里提到""我在笔记里写过""这篇文章我打算""下面我分三步讲"。
- 代码导读句和编辑指令："下面是……的实现""项目里的实现与下面的代码一致"
  "先补充几个 import""把以下代码放进……"。
- 先抑后扬与空过渡："不是……而是……"（全文最多 1 次）、"表面上看""很多人会以为"
  "值得注意的是""综上所述""总而言之""此外，"。
- 宣传腔与 AI 高频词："赋能""彰显""凸显""无缝""优雅""极致""奠定坚实基础"
  "标志着""见证了"。
- 协作痕迹与免责："希望对你有帮助""当然！""截至 XXXX 年"。

## 六、写完自查

是否回答了标题的问题 / 核心概念是否准确 / 是否讲了原理而不只是现象 /
结构是否连贯 / 有没有重复和凑字数 / 示例是否真的帮助理解 /
是否说明了适用条件与误区 / 是否适合初学者 / 有没有复习价值 /
有没有 AI 模板化表达 / 有没有未经核实的结论 / 代码命令链接是否核实过。
发现问题先改再输出。

## 七、封面提示词

在「高级技术杂志风」和「抽象概念视觉风」之间选一种：内容价值在"怎么用、怎么选、
怎么配、怎么排错"上走杂志风；价值在"一个结构为什么这样运转"且这个结构能画成
有空间关系的图时走抽象风。"文章里有机制"不足以选抽象风。

共同要求：16:9 / 1280×720；雾白、浅灰蓝、深蓝黑等低饱和配色；主色 2-3 种；
围绕一个核心视觉主体；不要机器人、芯片、代码窗口这类万能装饰；不要霓虹和过度发光；
不要水印和无关文字。

只输出可直接使用的图片生成提示词，不接任何出图 API，不产生出图费用。
